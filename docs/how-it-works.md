# How it works

This page follows the data from the files in this repository to a loaded Rock database.

## The pipeline

```mermaid
flowchart LR
    cal[Calibration scripts] -->|run on Rock databases| raw[Raw exports<br/>local only]
    raw --> norm[normalize.js] --> src[Anonymous source ratios]
    src --> prof[Profile<br/>sample-church.json]
    cast[Cast households<br/>and groups] --> builder
    conf[Configuration] --> builder
    pool[Address pool] --> builder
    prof --> builder[Builder]
    builder --> pkg[Dataset package<br/>core-1.zip]
    pkg --> loader[Loader]
    loader -->|bulk copy| db[(Rock database)]
    db -->|same calibration scripts| check[validate.js]
    prof --> check
```

1. **Measure.** The calibration scripts run inside a Rock database and return only anonymous counts and ratios.
2. **Normalize.** `calibration/normalize.js` turns that output into a source file of ratios. Raw exports never leave the git-ignored `calibration/raw/` folder.
3. **Blend.** A profile (`calibration/profiles/sample-church.json`) blends one or more sources into target numbers, and records each exclusion and override with a reason. `resolve-profile.js` produces the final numbers.
4. **Pack.** The [builder](../builder/README.md) reads the Cast, the configuration, the address pool, the photos, and the resolved profile, and writes one package per dataset for one Rock major release, such as Rock 21 (decision 52). A package holds data only, never SQL, and no dates are fixed in it.
5. **Load.** The [loader](../loader/README.md) checks the package, that it is new enough for the package, and that the database's Rock is the package's major release, read from Rock's `Rock.Version.dll`. Then it generates the timeline for the install day, and writes the dataset into a fresh Rock database.
6. **Grade.** The loader CLI runs the same calibration scripts against the loaded database, and `validation/validate.js` compares the results with the profile.
7. **Verify.** Before a package is published, the [verify tool](../verify/README.md) loads it into a clean copy of the Rock release it is built on, the newest dot release of its major, and checks it against Rock itself, then writes a receipt. Publishing needs a passing receipt. See [Verification](verification.md) for every check and why it is there.

| `cast/staff-emails.json` | The Cast staff's hand-written personal emails to Cast people | People designing test cases |

## One load, step by step

The loader runs the steps below in one database transaction. A failure rolls everything back, and `--dry-run` rolls back on purpose. Every inserted row carries `ForeignKey = SampleData:<dataset>`.

1. **Configuration.** Connection statuses, service time slots, campuses and their schedules, funds with a child account per campus, and check-in rooms. The Built on the Rock campaign fund gets the campaign's dates, and Rock's two pledge pages and default contribution statement point at it (see [Pledges](pledges.md)). It also sets up small groups: the capacity rule, the Host role, the group attributes, the topics, the inactive reasons, and a parent group per campus. Then it sets up serving: eight teams at every campus with their rooms, service times, staffing, and background check requirement, and Rock's Involvement connection type with the eight serving opportunities. Last, the church's own categories from `configuration/categories.json`, such as the Rock Solid Church data view category and its Group Sync child (decision 185).
2. **People.** Cast families, people, family memberships (including children shared between two homes), addresses with map points, and phones. For Full 7 and Core 3, generated households are added from the profile, and their small groups are planned before they load. Every campus also gets businesses: the Cast's 6 on the main campus, and at least 2 generated ones at each other campus. Each business has one or two contacts, loaded as Rock's Business Contact relationship. Cast staff join the security roles their stories give them, all roles Rock ships (decision 79). Alisha Marble loads into Rock's own admin person (Person Id 1) instead of a new person, so the `admin` login signs in as her (decision 177). The loader fills in what Rock's save hooks would set: ages, grades, giving Ids, giving leaders, primary family, and campus.
3. **Photos.** Every Cast person gets their delivered profile photo, except the few left without one on purpose. In Core 3, about half of the generated households get faces from a shared pool, one photo ethnicity per family. Full 7's crowd gets none.
4. **Attendance.** For each Sunday in the history window (3 years by default), each household attends at its own rate, adjusted for holidays and the month. Adults are recorded at worship. Children check in to the room their age or grade puts them in on that date, with a security code per family per Sunday. A student who comes on their own gets their own code. Students in grades 7 to 12 also come on their own: an engaged student comes on some Sundays the family stayed home, and some keep coming for a while after the family stops. Generated adults aged 18 to 20 check in as students until they graduate. Students are planned after every family, from their own seed, so adults and young kids are not affected (decisions 146 to 148).
5. **Achievements.** The Kids Check-in streak type and its seven achievement types, from High Five to Century Club. Each child who checked in gets a streak, and the achievement attempts Rock would have made at each of their check-ins. Next-gen check-in lists the seven types, so kiosks show each child's progress.
6. **Small groups.** The Cast's planned groups from `cast/groups` and the generated groups for each campus. Each group gets its schedule, its meeting place at the host's home (or a meeting link), its members, its attribute values, and its history. Weekly attendance follows the church year in [Small groups](small-groups.md): fall and spring seasons, a light summer, and holiday weeks marked "did not meet". Each Cast group gets a photo of its members, and Group Finder shows it on the group's card.
7. **Serving.** The Cast's rosters and generated volunteers at every campus, each with a rotation and preferences. Every Sunday in the history window, volunteers on their rotation serve when their family came and check in to serve; the next six weeks are scheduled ahead. See [Serving](serving.md).
8. **Connection requests.** A connected request behind every recent volunteer, people who just connected and wait as Pending, and active and inactive requests in the measured mix, each with its activity history. Team leaders connect them, except the main campus's new requests, which Alisha Marble connects (decision 178).
9. **Giving.** Each giving pattern produces gifts on its rhythm (weekly, bi-weekly, monthly, quarterly, irregular, occasional, year-end, or one-time). Gifts come through a channel: scheduled, online, in the offering, or a mailed check. They land in batches by day, campus, and channel, and checks always get batches of their own, because churches run them through a check scanner. Most couples give together as one giving unit, and about 10% give separately. Who pays how follows age and gift size, so older givers write most checks. Before the gifts are planned, the Built on the Rock pledges are planned: a pledger's usual gifts carry a campaign line sized to their pledge and how it is going, and some give extra campaign gifts. The pledges are written after the gifts, and both load only with the giving part. The fund's goal comes from the planned pledges and is written in every load (see [Pledges](pledges.md) and decision 126).
10. **Giving analytics.** The loader fills in what Rock's Giving Automation job would have written if it had run every night: each giver's giving attributes, giving bin and percentile, and journey stage with a year of history. Rock's own stored procedures do part of this work.
11. **Giving alerts.** The sample church's three alert types (Large Gift, Smaller Than Usual, Late Gift) come with the 12 months of alerts Rock would have raised.
12. **Prayer.** About 10 requests a week come in for every 1,000 adults who attended, gave, or were in a small group in the last year. Those adults ask most, and others on the church's records ask now and then, mostly once and a few several times, through the profile's months, weekdays, and hours. Each request gets a Rock prayer category by its weight in `configuration/prayer.json` and text built from that category's pool in `content/prayer`. A prayer administrator from the Cast approves most within hours, which sets them to expire 14 days later, and the newest few still wait for approval. The prayer team (the Cast's Prayer Team plus about 3% of active adults) prays through each approved request while it is active, each prayer a "Prayed" interaction, as Rock's prayer session records it. A few requests are flagged back to the approval queue, some get comments and a reply, and some older ones get an answer (decision 67).
13. **Notes.** The six note types on person records get their settings and View security (see [Configuration](../configuration/README.md#notes)). The Cast's hand-written notes from `cast/notes` load on every dataset. Generated people get notes built from the text pools in `content/notes`: who gets notes and how many follow the designed targets in the profile, and the day and time follow the measured shape. Some notes get replies from other staff, a few are alerts, private, or pinned, and some mention another staff member.
14. **Steps.** Rock's Discipleship Path is built out to seven steps from `configuration/steps.json`, and every step comes from a record the earlier steps wrote (decision 86). Small Group, Serve, and Lead steps follow each small group and serving team membership, read back from the database. Give steps follow the giving journey, replayed every Tuesday night over the history window. Baptism steps follow the Baptism Date, which generated adults get here, with Baptized Here on the step and the person. Starting Point Class and Foundations fall on real class dates that count back from the install day: every volunteer took Starting Point before serving, a few people per campus are in each current class, and the rest follow designed shares of active adults. The Student Path is a second program from the same file. Its steps follow the student check-ins the attendance step planned: Student Camp and Mission Trip on church-wide event dates, Follow Jesus at camp or on a Sunday the student came, and Student Leader from August of junior or senior year to graduation, each for a designed share of the students who could. Many students who decide to follow Jesus are baptized on a later baptism Sunday, often the July one after camp, on the same Baptism step. People whose Complete steps cover every step type in a program get a completion for it, the way Rock's Update Step Program Completions job records it. See [Steps](steps.md).
15. **Communications.** The church's texting numbers: a main line, a student line, and staff personal numbers, with one for each campus pastor on Full 7. The branded "Rock Solid Church" email template with the approved logo. A weekly newsletter list per campus, seven ministry and staff lists, and two care lists, New Here and We Miss You. Who is on each follows involvement: involved adults get their campus newsletter, Leading and Engaged adults opt in to more lists, and the Volunteers, Small Group Leaders, and Prayer Team lists copy the teams, the leaders, and the prayer team. Nobody who chose "No mass emails" or "Do not email" is on a list. Then two years of bulk email: each campus's weekly newsletter, church-wide emails to each campus's involved adults, and ministry emails, each recipient sent or refused the way Rock's send path decides, with opens, clicks, bounces, unsubscribes, and the History lines Rock writes. Then two years of texts: mass texts on the main and student lines with their replies and STOPs, the Cast's hand-written threads, and generated conversations, mostly on staff members' personal numbers. Then two years of one-to-one email: serving confirmations and reminders, connector follow-ups, prayer celebrations, first-visit welcomes, and the Cast staff's personal emails. Then the church's app, its devices, and two years of pushes with their opens. Then the messages tied to steps: class emails and texts, baptism follow-ups, and the finished After Starting Point flow. Last, five group syncs: data views that keep the Volunteers, Small Group Leaders, New Here, and We Miss You lists and the RSR - Prayer Access role in step, each group filled as Rock's Group Sync job would leave it on install day, so the job's first run changes nobody and sends nothing. See [Communications](communications.md) and [Group sync](communications.md#group-sync).
16. **Calendar.** The church's 51 events on Rock's Public and Internal calendars, with their audiences and photos. Each event gets an occurrence for each campus and start time, from the start of the history window to 13 months ahead, with its own schedule, place, and contact. Dates follow the rules steps and messages use, so Easter, the baptism Sundays, the classes, camp, and VBS fall on the same days everywhere. Rock's four sample events become church events in place. See [Calendar](calendar.md).
17. **Registrations.** Event registration setup for camp, the mission trip, the fall retreat, VBS, Parents' Night Out, Serve Day, Money Matters, Date Night, and the Women's Retreat: template categories, templates with forms, fees, discounts, and placements, and each year's instances linked to their calendar occurrence with a public name and URL slug, their linked group, and their placement groups. Seven registrations are open on every install day. Nobody has registered yet; later slices add the people. See [Event registrations](registrations.md).
18. **Logins** (when the person installing gives a password). The Cast's logins from their files, each campus pastor's, and a designed share of generated adults from `configuration/logins.json`, all with the one password, hashed the way Rock's Database login stores it. Each login has the person history Rock writes. Every load also sets each person's account protection profile the way Rock does. See [How logins load](../loader/README.md#how-logins-load).
19. **Cast and business expectations.** The loader checks that key Cast people show what their stories say, for example that the Deckers are monthly, consistent givers, that Sam Lee has earned Century Club, that Ted Decker has completed the Discipleship Path, and that Jasmine Washington has completed the Student Path, that each staff texting number belongs to its staff member, that Kevin Dawson left the Men list and Brandon Watson chose "No mass emails", that each Cast text thread shows in its intended state, and that each Cast staff email shows in the person's Communication History. It also checks that each campus has its minimum number of businesses, and that every business has a contact and a gift in the last 12 months.
20. **Check images** (optional, `--check-images`). Each recent check gift gets a scanned front and back that match the gift.

## Dates and repeatability

- Every date in a data file is relative: `yearsAgo` plus a month and day, or `daysAgo` for recent events.
- The **anchor** is the date everything counts back from. It defaults to today on the database server, the clock Rock Cleanup uses for ages (decision 152). Pass `--anchor yyyy-MM-dd` to pin it.
- Every random choice comes from a stream seeded by the `--seed` text and the household. The same seed and anchor give the same data, row for row.

## The tools

| Command | What it does |
|---|---|
| `node cast/validate-cast.js` | Checks every Cast file: required fields, Guids, cross-references, statuses, and photo rules. |
| `node cast/build-pages.js` | Rebuilds the family pages in `cast/families/` from the household files. |
| `node addresses/build-pool.js` | Rebuilds the address pool. Add `--cast` to give Cast households addresses. |
| `node calibration/normalize.js` | Turns calibration output into a source file, or into a scratch file with `--out`. |
| `node calibration/resolve-profile.js` | Resolves a profile into final target numbers. |
| `dotnet run -- --rock <Rock checkout>` (in `builder/`) | Writes one package per dataset to `packages/`. See [Builder](../builder/README.md). |
| `dotnet run -- --package <file.zip> --connection "..."` (in `loader-cli/`) | Loads a package. It also runs calibration (`--calibrate`), the Cast expectations check (`--check-cast`), and the giving parity test (`--giving-parity`). See [Loader](../loader/README.md). |
| `dotnet run -- --plan-cast-groups` (in `builder/`) | Plans the Cast's small groups into `cast/groups`. Rerun it after a Cast or small group rule change, then rerun `build-pages.js`. |
| `dotnet run -- --deliver-photos <batch.json>` (in `builder/`) | Keeps new generated photos' originals, saves their 400-pixel copies, and adds them to the photo manifest. See the [photo brief](../photos/brief.md). |
| `node validation/validate.js` | Grades generated data against the profile. |
| `node validation/check-rock-lock.js` | Checks Rock on GitHub for changes to the code the loader ports. See [Validation](../validation/README.md#rock-version-guard). |
| `validation/achievement-parity/` | The achievements parity test. It runs Rock's own streak and achievement code on a loaded copy and compares the results with the loader's rows. See [Validation](../validation/README.md#the-achievements-parity-test-before-each-release). |
| `node validation/check-standards.js` | Checks the content standards that span folders: phones, emails, raw data, and calibration source labels. |
| `dotnet run -- --rock <Rock checkout>` (in `verify/`) | Proves each package works on its Rock and writes a receipt. Add `--check-receipts` for the publishing gate. See [Verification](verification.md). |

## Where the loader goes

The loader CLI installs packages for developers and test harnesses. A block inside Rock calls the same loader library through the `SparkDevNetwork.Rock.SampleData.Loader` NuGet package, which builds for the .NET Framework Rock runs on. A person picks the parts to load, and the loader refuses a database that already has people (decisions 120 to 122). Later, configuration will save through Rock's own services. Rock will never depend on this repository; everything it needs arrives in the package.
